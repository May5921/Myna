# AI 开发者 / Agent 工具的 GitHub 机会地图

**Research question:** 面向 AI 开发者 / Agent 工程师，哪些尚未被充分满足的高频痛点，最适合在 2026 年做成一个开源工具，并同时具备可演示、可复制和 GitHub 自传播的条件？

**Background / motivation:** 目标是从零寻找一个新的开源工具方向，优先获得 GitHub 的自然增长，而不是为现有 Myna 产品寻找增长切口。需要先识别真实、重复出现且有公开证据支持的痛点，再判断哪些痛点能形成清晰的最小产品和 GitHub 原生传播循环。

**Hypotheses:**
- **H0（空假设）：** 现有公开证据无法支持某个新切口明显优于其他切口。
- **H1（方向性假设）：** 至少能找到 3 个切口，同时满足反复出现的痛点、现有方案存在明显缺口、15 分钟内可演示、输出物可分享或复用这四个条件。

**Population & unit of analysis:**
- 人群：使用模型、Agent、评测、工具调用、检索或自动化工作流的 AI 开发者 / Agent 工程师。
- 分析单位：一个候选工具机会（一个明确用户痛点与对应产品形态的组合），而不是一个仓库或一条帖子。

**Key variables (operationalized):**
- 痛点频率：公开 Issue、讨论、论坛帖和重复提问中，同一问题出现的独立来源数量与时间跨度。
- 痛点强度：问题是否阻塞工作、造成重复人工操作、错误成本或明显的调试时间。
- 现有缺口：现有工具是否只能部分解决、安装/配置成本是否过高、是否缺乏可解释结果或缺少可组合接口。
- Demo 可见性：从安装到首次看到价值是否能控制在 15 分钟内，且结果能用截图、日志、报告或可运行样例展示。
- 复制性：用户能否用自己的仓库、数据或模型复现价值；贡献者能否通过插件、规则、适配器、数据或文档参与。
- GitHub 传播循环：工具产出的报告、Trace、评测结果、模板、规则包、插件或项目文件是否会被用户分享、Fork、引用或提交改进。
- MVP 可行性：在 2–4 周内能否由小团队做出可运行的核心闭环，不依赖未确认的商业 API 或大规模训练。

**What counts as an answer:**
- 输出 5–10 个候选方向的机会地图。
- 每个方向都要写清用户、痛点、现有替代、开源优势、传播循环、MVP 和主要风险，并给出证据等级。
- 至少 3 个方向达到 H1 的筛选条件；若达不到，明确报告“没有足够证据”。
- 依据证据选出 1 个首攻方向，并说明暂不选择其他方向的原因。

**Scope & exclusions:**
- 只研究 AI 开发者 / Agent 工程师工具。
- 只研究开源或可开源的产品形态。
- 不把只接一个模型 API 的薄壳、缺乏独立工作流价值的聊天界面或单纯换皮项目视为优先机会。
- 不承诺“爆款”；结论只表示证据支持的优先级和下一步验证方案。
- 不进行付费投放、生产部署、真实用户数据写入或外部服务配置变更。

**Open questions for prior-work survey:**
- 近年增长较快的 AI 开发者工具，哪些增长来自真实使用，哪些主要来自发布时的注意力峰值？
- 哪些公开信号最能区分“高频痛点”和“少数人的抱怨”？
- 哪些输出物最容易形成 GitHub 的分享、Fork、插件或贡献循环？
- 目标候选方向的安装和首次成功路径是否足够短，能否在不牺牲安全性的情况下演示？
